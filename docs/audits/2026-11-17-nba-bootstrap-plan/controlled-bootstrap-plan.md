# Controlled FINAL-only bootstrap — design, not production authorization

Target, if separately approved: existing dashboard SQLite Durable Object namespace `fc70a55e49c84d28bacc562a8d5cfb62`, named object `capture:nba`, existing tables `nba_history_versions` and `nba_history_checks`. No new namespace, service, credential, binding or dashboard deployment is needed to stage historical inputs. CW08 and all ledgers are outside scope.

The existing authenticated Cloudflare Data Studio SQL API (`query/v2`) has supported the prior read-only inspection. Its prospective write mode has **not** been exercised here. The offline rehearsal uses actual DO `transactionSync`; do not assume multi-request Data Studio calls have that transaction guarantee. There is no production sender in this change.

## Required future sequence

1. Pin the source commit, exact gzip SHA/digest and archive manifests. Revalidate the plan using the existing validator at the actual import clock, preserving original `observedAt`/`lastVerifiedAt`. Admit FINAL-only sources. Stop on any checksum, timestamp, census or identity mismatch.
2. Reconfirm separate approval, object identity, backups, current fallback and capture holds; snapshot current evidence rows and protected-ledger inventory read-only. Require an audited exclusive import window or an equivalent atomic conflict guard; no competing evidence writer may invalidate the snapshot. Do not change Worker schedules/bindings as an incidental part of importing.
3. Compare every source against active pointers and staged versions before any write. Identical validated existing source/hash: skip, with no timestamp update. Any conflicting, invalid or unrecognized version/pointer: stop for review. Verify table schema, total stored bytes and headroom. Do not call the store's general upsert against existing sources.
4. Stage **only absent immutable versions**, using the existing canonical envelope and gzip/base64 encoding. Use bounded parameterized batches (at most ten sources and 128 KiB encoded payload per batch). A duplicate must first be proved byte-identical; `INSERT OR IGNORE` alone is not integrity verification. An interrupted stage leaves inert versions, not newly active evidence. Read every staged body back, decode and compare canonical SHA, provenance and original times before publishing.
5. Publish only absent active-check pointers, after all staged bodies pass verification. Require one atomic guarded statement or a documented DO transaction that checks the entire precondition and aborts the entire activation on any source conflict/concurrent change. Never assume a sequence of remote SQL requests is atomic. Existing check rows are never updated. Stop if the authorized SQL interface cannot implement that guarantee; do not improvise a public endpoint or deployment.
6. Read back all activated source hashes and original timestamps, count duplicates/new entries, and compare the pre-existing evidence and protected-record inventories. Save a checksummed receipt containing plan digest, before-state hash and **only introduced pointer keys/hash/verified times**. Record `consumerActivated` separately and conservatively. Do not activate a prediction consumer merely to test the import.
7. Before any consumer uses these inputs, rollback may deactivate only the new pointers after an all-or-nothing compare-and-swap check against the import receipt. Leave immutable source bodies for provenance; retain existing pointers/records. A newer collection timestamp/hash invalidates destructive rollback. Once a consumer may have used the evidence, use compatible Worker/logical fallback and retain all evidence, projections, picks and grades. Never restore the ledger database or delete later observations to roll back this seed.

## Verified versus still required

Verified offline: canonical validation/store compatibility, original timestamps, duplicate/no-overwrite handling, interrupted atomic local transaction, exact source readback, process restart, rollback scope, later-write refusal and no ledger mutation in an isolated SQLite runtime. The rehearsal helper has no network or production bindings.

Still required before a real import: separate approval; a reviewed authenticated sender using existing permissions; actual remote write/activation atomicity proof; fresh current before-state/occupancy inventories; readback and recovery receipts. This plan does not authorize those actions. If the safe write channel is unavailable, stop rather than deploying another Worker or transferring credentials.

Fresh discovery remains independently mandatory after any bootstrap. A stored FINAL census does not certify that a player's event list is current. Preserve the existing 15-minute discovery freshness, 48-hour final lag, history window, minimum-history and all model/EV rules. A successful seed alone is not a successful cold-start forecast or a production acceptance pass.
